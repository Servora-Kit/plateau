# OIDC Provider 与服务令牌

- Provider 与 `AuthenticationUsecase` 共用 `biz.NormalizeOIDCIssuer` 校验并规范化 issuer（仅允许 HTTPS 或符合 RFC 6761 的回环主机 `localhost`、`127.0.0.1`、`::1`、`*.localhost`），`NewOIDCStorage` 校验 `auth_request_ttl > 0`（默认 30m）与 `service_access_token_ttl > 0`；`app/iam/service/cmd/keygen` 复用 `internal/oidc` 的密钥校验逻辑幂等生成/轮换 `0600` 权限的 RSA-2048 PKCS#8 PEM 签名私钥与 32B 加密密钥（多副本部署须由一次性初始化任务写入共享 Secret，严禁副本各自生成临时密钥）。静态 client 和密钥元数据在服务可用前协调，见 [启动](startup.md)。
- 授权请求限定 authorization-code、query response mode、PKCE S256 与 `openid` scope；发现文档声明 `authorization_response_iss_parameter_supported: true` 及 `token_endpoint_auth_methods_supported: ["client_secret_basic", "client_secret_post", "none"]`，`/authorize` 与 `/authorize/callback` 写入 `Cache-Control: no-store`，且在发往客户端外部 `redirect_uri`（含 `code` 或 `error`）的 3xx 跳转中统一经 `redirect_writer.go` 注入 RFC 9207 `iss`（内部 `/authorize/callback`、`/login`、`/consent/` 跳转不注入 `iss`）；用户在登录流或授权同意页点击取消/拒绝时销毁未完成的 `oidc_authorization_request` 并组装 `<redirect_uri>?error=access_denied&state=<state>&iss=<issuer>`。
- OAuth 客户端区分 `STATIC`（配置文件引导，只读）与 `DYNAMIC`（`OAuthClientService` gRPC 管理），支持 `WEB`、`USER_AGENT`（强制 `none` 公共客户端）与 `NATIVE`（允许自定义 Scheme 及 RFC 8252 回环动态端口）三类应用。`/oauth/token`、`/oauth/introspect`、`/revoke` 仅接受 `POST`，拒绝 URL Query 携带 `client_secret`、拒绝同时携带 Basic 与表单密钥或 `client_id` 冲突，并在 `AuthorizeClientIDSecret` 中严格校验客户端 `active` 状态、实际认证传输方式与 `token_endpoint_auth_method` 完全一致，以及对全部未过期 `oauth_client_secrets` 执行常量时间比对。禁用或删除客户端在单事务内级联失效关联 `auth_flows`、清理未完成授权请求、消费授权码并撤销活跃令牌会话；`activeAccessToken` 与刷新令牌交换均校验所属客户端处于 `active` 状态。
- 授权回调先确认 SCS 已加载并解析活跃身份与非空 `amr` 的登录会话（空 `amr` 防御性重定向回 `/login?request_id=...`），不绕过 [会话校验](sessions.md)；随后由 `CompleteAuthorizationRequest` 在单事务内校验客户端活跃与 `trusted` 策略，对需用户授权的第三方客户端（`trusted=false` 且首次授权、请求新增 Scope 或携带未确认的 `prompt=consent`）写入会话 `consent_owner_hash` 并引导至 `/consent/?request_id=<id>`。
- 授权请求完成、code 保存、人类令牌签发/刷新与 userinfo 投影均须校验非软删除 `ACTIVE` 身份、主邮箱已验证且 `required_actions` 为空；`CompleteAuthorizationRequest` 拒绝空 `amr` 并将 `LoginSession.Amr` 复制至 `OIDCAuthorizationRequest.Amr`，经 `OAuthTokenSession` 透传至 ID Token 与刷新令牌；code 与 refresh 发行在事务中锁定身份，code 条件消费，refresh 轮换消费旧 token 并建立后继，重放已消费 refresh 时撤销对应 OAuth 会话并返回 invalid grant。
- 服务 token 仅发给允许 `client_credentials` 且已注册 audience 的 client，不提供 refresh token，access-token TTL 必须为正。IAM 签发的 JWT Access Token 统一写入 `token_use=access` 与对应的 `actor_type`（人类令牌为 `human`，服务令牌为 `service`）；ID Token 不携带 `token_use=access`。
- 服务认证通过 `security/authn/jwt.ServerFor[jwt.ServiceClaims]` 强制校验 `token_use=access`、`actor_type=service`、`sub=client_id`、签发时间与 token ID，并校验 issuer 和接收服务声明的 audience（人类 Access Token 与 ID Token 均被服务接口拒绝）。
- token 校验仅产生身份，不产生额外管理权限；接收服务独立执行 [授权](authorization.md)。
- `internal/oidc` 协议引擎不直接依赖 `audit.Auditor` 或 `cloudevents`；原生 OIDC HTTP 审计由 `oidc.RegisterHTTPServer` 在路由层外包 `security/audit.HTTPHandler` 完成，内部仅通过 `ctx` 被动补充身份、客户端与错误标记，未登录常规 `302 /login` 引导与成功的 `/oauth/token` 请求不产生审计事件。`admin` 服务客户端默认配置双受众 `audiences: [iam, audit]`，由启动期 `OIDCInitializer` 幂等同步。

# 平台与母框架边界

Plateau 承载平台业务、主要参考应用和具体安全生态；Servora 是独立演进的母框架。规范归属按责任确定，不因两个仓库能在父级 `go.work` 中联调就合并职责。

| 内容 | 权威归属 |
| --- | --- |
| 平台总体结构、具体 AuthN/AuthZ、OpenFGA 适配、安全插件 | `plateau` |
| 平台源 Proto、注解声明、共享生成产物 | `api` |
| 平台共享 client | `web` |
| 微服务如何分层和使用 Servora | `service` |
| 母框架自身 CRUD、启动、transport、provider、审计、CLI | `servora` |
| 应用定位、领域模型、业务流程与前后端 | `<应用>/architecture.md`、`backend.md`、`frontend.md` |

## Servora 协同迭代

Plateau 开发和 dogfood 中发现 Servora 的缺陷、通用能力缺口或可复用的优化需求时，先根据复现、调用契约和源码确认责任归属。确属框架职责的，优先在 `../servora` 中修复、补齐或优化，再由 Plateau 接入，避免同一问题在消费方形成长期补丁。

- 修改前读取 [Servora 对应层规范](../../servora/index.md)；修复落在能力所属源码或生成器中，消费方按更新后的契约使用。
- 禁止通过业务侧重复实现框架逻辑、吞错、静默降级或跳过必要逻辑来掩盖框架问题，也不能把绕过后的结果当作验证成功。
- 业务专属的领域规则、授权 scope 和数据编排仍由 Plateau 拥有；集成或配置使用错误在所属消费方修正，不因联调方便迁入 Servora。
- 暂时无法在 Servora 修复且确需临时适配时，向用户明确说明，并在任务记录或变更说明中记录问题依据、无法直接修复的原因、适配位置、影响及移除条件；框架修复接入后移除对应适配，不得作为无记录的永久分叉。
- 为框架修复补充能复现问题的回归验证，同时验证 Plateau 受影响的实际消费路径，记录测试或 dogfood 结果。涉及生成器时核对实际调用版本并重新生成，遵循 [生成入口与来源约定](../../api/proto/generation.md)；仅有 `go.work` 联调或 Servora 单侧测试通过，不代表 Plateau 接入已验证。

## 身份与业务

IAM 是平台自用的全局身份池，拥有稳定且不可复用的用户 ID、凭据、会话与签发职责。业务 tenant、membership 和资源隔离由各业务服务拥有；业务投影通过 `iam_user_id` 引用 IAM，不复制凭据或向 IAM 填业务资料。email 变化不改变用户 ID。

IAM 自建领域模型，复用 OIDC 协议库；使用协议库不意味着把 IAM 产品生命周期托管给外部 IdP。共享 Actor 只表达已确认执行身份，不能携带业务角色列表冒充实时授权。

Admin 是管理入口，被管理服务仍拥有领域事实；应用定位与接入设计见 [Admin 架构](../../admin/architecture.md)。用户本人管理身份资料、认证方式和登录会话属于 [IAM 账号自助管理](../../iam/architecture.md)；个人页面汇集其他产品入口，不改变各产品的数据与规则归属。

## 生成与消费

`@plateau/api` 承载可再生成契约，`@plateau/client` 承载手写 transport 与框架中立错误事实。Cookie/token 持久化、登录跳转和业务文案属于应用；生成目录不容纳手写 runtime。框架内部与业务消费规范通过链接组合，不复制两套规则。

当前内部 Example 是有效参考；Audit 明确停止维护、等待重构。新增服务优先按共通规范和 Example，不能把 Audit 的现状推广为推荐架构。独立 servora-example/servora-transport 的扩展不随平台规范任务自动纳入。

检查：新规则是否有一处权威来源；当前实现是否与既定边界不同；差异是否被显式记录。不要通过规范整理悄悄修改产品范围。

# 0 号任务：从 OpenSpec 切换到 Trellis 的项目规范建设

**本文件供开发者与 AI 共同阅读、讨论和审阅，用于确定规范迁移的目标、范围、约束与验收标准。**

## 目标与背景

以 Plateau 为日常开发入口，在现有 Trellis 0 号任务中重新梳理并确立项目开发规范，将开发者明确的约定、有效项目文档和当前实现证据组织成 Trellis 规范体系，使后续任务能够按职责找到并组合所需规范。

Plateau 是主要业务开发方向；Servora 是持续渐进迭代的独立母框架。此次工作将初始化生成的 `.trellis/` 整理为按项目职责组织的规范体系，包含规范建设和历史 OpenSpec 核对。package 配置在规划阶段已同步，实施阶段沿用该配置。

任务沿用 `.trellis/tasks/00-bootstrap-guidelines/`。开发者发出“开始执行”后，已通过原生任务命令激活真实会话并进入实施。完成情况以本文验收清单及 `research/verification.md` 的证据为准；任务状态本身不能替代验收结果。

## 范围

### 本任务包含

- 按已确定的职责修正 `.trellis/config.yaml` 中的 package 映射与默认 package。
- 重组并填写 `.trellis/spec/`，建立共享规范、母框架规范和业务微服务规范。
- 整理并确立开发者在本任务中明确的项目结构、职责边界与编码风格；记录既有代码与确认规范之间的差异。
- 从当前源码、测试、配置与有效项目文档提炼规范，再核对历史 OpenSpec，记录覆盖情况与差异。
- 准备与本任务复杂度相符的中文需求、设计、实施资料及任务上下文。
- 同步与最终规范结构直接相关的任务元数据、索引和必要的 AGENTS 导航。
- 验证 package 与规范发现、文件引用及任务上下文的实际加载。

### 本任务不包含

- 工作区联调调整：Go、pnpm、Buf、Just 编排及现有跨仓引用方式均沿用现状。
- 业务代码修复、生成代码重建、依赖升级、部署和运行环境搭建。
- 仓库搬迁、配对 worktree、独立 Transport 仓库合并。
- Trellis 上游、全局安装、全局 Codex 配置或 hooks 的改造；本地脚本仅包含 R3 所需的包根索引发现兼容。
- 历史 OpenSpec 的搬迁或删除，也不重新建立一套并行的 OpenSpec 变更流程。
- 独立 `../servora-example`、`../servora-transport` 仓库的扩展开发。

发现业务缺陷、技术债或配置与目标不符时，记录其证据和影响，另行处理。

## 需求

### R1：建立五个必备的共享与框架 package

| Package | 源码路径（相对 Plateau 根目录） | 规范职责 |
| --- | --- | --- |
| `plateau` | `.` | 项目结构、平台边界、总体约定，以及 Plateau 自身共享能力的设计与实现规范 |
| `api` | `api` | Proto、注解、生成流程与生成物归属 |
| `web` | `web` | Plateau 共享前端能力；当前包含 client 的设计理念与使用规范，后续按实际能力扩展 |
| `service` | `app` | Plateau 推荐的微服务组成、分层职责、依赖方向、协作方式及 Servora 使用约定 |
| `servora` | `../servora` | 母框架自身的开发规范 |

- 默认 package 为 `plateau`，必须匹配配置中的实际键名。
- package 按规范职责划分，无须与 Go module 或 pnpm 包逐一对应；允许源码范围重叠。
- Servora 保持独立 Git 仓库边界；其 Git 上下文标识与源码、规范映射分别说明，不赋予其联调或发布职责。
- `api/gen` 及 Servora 生成目录不建立独立规范 package；生成约束归源定义或相应消费方。
- 当前 client 纳入 `web`，不再单设 `client` package。
- 未来新增共享前端能力时扩展 `web`，不预建没有实际内容的规范。

### R2：业务微服务按应用与端划分 package

存在 `app/<应用>/service` 或 `app/<应用>/web` 的业务应用，分别使用 `<应用>-service`、`<应用>-web` 作为 Trellis spec package 名，并映射到对应源码目录。

当前已有实现的范围包括：

| Package | 源码路径 | 规范职责 |
| --- | --- | --- |
| `iam-service` | `app/iam/service` | IAM 后端独有的领域模型、流程与设计规范 |
| `iam-web` | `app/iam/web` | IAM 前端独有的设计规范 |
| `example-service` | `app/example/service` | Example 后端独有的设计规范 |
| `example-web` | `app/example/web` | Example 前端独有的设计规范 |
| `audit-service` | `app/audit/service` | Audit 的现有设计、维护状态和适用限制 |
| `test-web` | `app/test/web` | 测试前端的用途与开发约束 |

- 新增或现有其他应用端遵循相同命名规则；仅有占位目录时标明现状，不编造实现规范。
- Plateau 内部的 `app/example` 继续作为有效参考应用，与暂停扩展的独立 `../servora-example` 仓库区分。
- Audit 的维护状态以当前代码和有效文档为依据；停止维护的实现不得直接作为新增微服务的推荐模式。

### R3：按实际主题组织规范，保留有效索引

- 预生成模板仅作为起点，可以按项目实际情况删除、重命名、拆分或新增 Markdown 文件。
- 每个实际承载规范内容的目录应有 `index.md`，说明适用范围、开发前检查、质量检查，并索引该目录的实际主题文件。
- 规范层和文件名按能力、领域或工程主题命名，不强制使用 `frontend`、`backend`，也不机械复制默认模板的文件清单。
- 业务端 package 的 `-service` / `-web` 已表达前后端，`index.md` 与主题文件直接放在包根，不再套重复的 backend/frontend 目录；共享 package 保留有实际职责含义的分组。
- 本地包发现输出须同时识别包根索引和实际子层；此次允许为上述目录调整补充必要的本地发现兼容与回归检查，不扩展配置 schema。
- Plateau 的 `security/`、`infra/`、`cmd/`、`internal/codegen/` 归入 `plateau` package，按能力组织相应规范层；项目级总体约定与各能力自身的实现规范分别表达。
- 根 `cmd/` 当前的 AuthN/AuthZ 插件与共享生成实现共同归入平台代码生成规范；以 `cmd.md` 记录命令职责和使用边界，不单设 `cmd` package。业务微服务的 `service/cmd/` 仍归各业务端及共通微服务规范。
- `plateau` 范围应包含 `authN.md`、`authZ.md` 等实际主题，`servora` 范围应包含 `audit.md` 等框架主题。完整主题清单和具体层级由源码证据确定，并在设计文档中明确。
- `servora` 的审计能力规范与 `audit-service` 的业务服务规范分别维护，明确框架能力与消费方的边界。
- 保留通用 `guides`；长期项目约定进入其所属 package，临时研究和迁移差异进入任务资料。
- 最终组织方式须与当前 Trellis 的规范发现和任务读取机制兼容；存在 `index.md` 本身不等于已通过加载验收。

### R4：共享规范与业务规范明确分工

- `service` 记录微服务共通规范，`<应用>-service` 补充领域模型、业务流程和确有需要的特有约束。
- 共通微服务规范应分别说明项目目录布局、内部职责分层和推荐编码方式；覆盖 `server`、`service`、`biz`、`data` 各层，以及启动装配和跨层共通编码约定，并提供有源码依据的示例与检查要求。
- 基础工程约定应覆盖各层测试与依赖替代、集成验证条件和质量检查入口，以及错误转换、日志记录边界、context 传递、配置加载和资源清理；框架与业务应用补充各自差异，不将单一应用写法直接推广为共同规则。
- API 规范应覆盖资源命名、分页／过滤／排序、字段选择与更新语义、错误契约和兼容性要求；消费方引用这些契约，不重复维护。
- Servora CRUD 的使用流程与推荐写法属于共通微服务规范，以 `app/example/service` 为主要参考。应串联 service、biz、data 各层的协作，覆盖 `ResourcePlan`、`ListPreparer`、`ResourceNameMatcher`、`ListFields`、`ResourceMapper`、`ClearHelper` 的声明与构造，以及 `service.plan.ToResponse`、`entcrud.NewListFields`、`entcrud.Columns`、字段绑定（`bind`）、`repo.mapper.ToDTO` 等配置和调用方式；不能仅列出 API 名称。框架内部契约归 `servora`，Example 特有业务规则归 `example-service`。
- 根 `AGENTS.md` 的“目录结构”章节直接作为 Plateau 结构规范的正文基础；`app/AGENTS.md` 的“服务结构”章节按目录布局、职责分层和各层文件约定分别整理，保留其中的有效约束。
- `internal/server/` 的生产代码通常只包含 `server.go`、`grpc.go`、`http.go` 及 `sse.go`、`asynq.go` 等具有服务端职责的文件。
- biz 业务文件按 import、必要的业务常量／变量、一组或多组 `XxxRepo` 接口、`XxxUsecase` 结构体、`NewXxxUsecase`、Usecase 方法的顺序组织；data 实现文件按 import、私有 `xxxRepo` 结构体、构造该实例的 `NewXxxRepo`、实现 `biz.XxxRepo` 的方法组织。
- 应用特有模块按 IAM 的现有习惯放在服务的 `internal/` 下，例如 `oidc/`、`authn/`、`mail/`、`startup/`；其职责仍需明确，不能强行塞入四个通用层或提升为平台共享能力。
- `web` 记录共享前端能力，`<应用>-web` 记录应用自己的目录组织、路由、组件与状态职责、请求和生成 API 的使用、加载与错误状态，以及业务交互；不同前端按实际框架与应用规模表达，不强制统一实现方式。
- `plateau` 记录平台共享能力自身的约束，`service` 记录业务微服务如何使用这些能力。
- `servora` 记录框架内部开发约束，Plateau 消费框架的规则归 Plateau 的相关 package。
- 共同规则保持一处权威定义，通过明确引用组合；应用特有差异说明原因和适用范围，避免复制整套共享规则。
- package 之间不假定存在自动规范继承；任务应显式加载所需的共享、框架和业务规范。

### R5：结合确认约定与当前实现建立基线，核对历史 OpenSpec

- 先结合开发者已确认的约定，读取当前源码、测试、配置、AGENTS、README、有效 ADR 等证据，形成独立的规范基线；再对照 `../openspec/specs/`，归档历史按需读取。
- 开发者明确的约定本身属于规范依据。现有代码尚未遵循时，区分推荐规范与当前实现并记录差异；不因旧实现存在而削弱已确认规则，也不把本轮未执行的代码整改写成已经完成。
- 每项重要规范应引用真实文件、契约或适用示例；对共通模式尽量提供多个真实实例，单一实例则准确限定适用范围。
- 历史 Requirement/Scenario 的核对结果应可追溯，区分已实现并验证、代码或配置存在但未验收、旧规范未实现、已过时、待确认。
- 保留仍然有效的工程约束和设计意图；源码与历史文档有冲突时，分别记录实际行为、约束依据与待处理差异，不把缺陷直接推广成推荐惯例。
- 计划中的能力、配置中的能力和经过运行验证的能力应明确区分，未执行的检查不得表述为已验收。
- 历史 OpenSpec 保持原位，不整套搬入 Trellis，也不将此次规范建设扩展为业务实现变更。

### R6：规划资料和任务上下文可审阅、可加载

- 任务资料使用中文，代码标识符、配置键、命令和路径保留原文。
- 当前规划讨论先记录开发者提出的规范重点和参考入口，不展开大范围源码调查；具体调用流程、API 契约与示例差异在实施本任务、编写规范正文时逐项细看。
- `prd.md` 记录目标、范围、约束和验收；`design.md` 记录规范结构、归属、迁移及上下文设计；`implement.md` 记录有序执行清单与验证方法。
- 本次涉及多个 package、规范重组及历史核对，按复杂任务准备上述三份资料；文件名为 `implement.md`。
- 子代理工作流所需的 `implement.jsonl`、`check.jsonl` 只承担规范和研究文件清单职责，不能代替实施文档。
- 上下文清单必须引用真实存在且确实相关的文件，并显式列出需要加载的正文；索引链接不会自动展开为全部内容。
- 同步现有 0 号任务的关联范围，保留任务身份及真实状态，不重复初始化或创建平行任务。
- 记录实际发现与读取证据；自动注入未验证或不可用时如实说明，按本地工作流显式读取，不因静默跳过文件而宣称验收通过。

## 验收标准

- [x] R1：五个必备 package、源码路径和默认 package 正确；配置无重复键，不再把生成目录或 client 单独列为 package。
- [x] R2：业务端采用 `<应用>-service` / `<应用>-web` 命名，映射实际源码；维护状态、占位状态和参考应用边界准确。
- [x] R3：实际规范目录均有有效索引；主题文件按能力组织，覆盖已明确的认证、授权、框架审计等主题，无空模板或虚构实现。
- [x] R4：共享、框架、业务规范职责清晰；指定 AGENTS 章节的有效内容得到保留；共通微服务规范覆盖目录布局、职责分层、server 文件边界、biz/data 声明顺序、应用特有 internal 模块的归属，以及 Servora CRUD 的完整使用流程和推荐写法；跨 package 组合与应用差异可追溯，无重复维护的整套规则。
- [x] R4 基础覆盖：测试与质量检查、错误／日志／配置／生命周期、API 契约与兼容性，以及业务前端基本组织均有明确规范归属和当前依据。
- [x] R5：重要规则有开发者确认、当前源码或有效契约依据，当前实现与规范之间的差异及历史 OpenSpec 核对状态可查，未验证能力没有被写成已验收。
- [x] R6：中文 PRD、设计、实施资料齐全，任务元数据与上下文一致；规范发现、文件引用和实际加载经过检查并记录结果。
- [x] 变更限于本任务的规范、必要配置、任务资料和导航，保留用户既有改动；工作区联调、业务代码、历史 OpenSpec 及其他排除项保持现状。
